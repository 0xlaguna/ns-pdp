# Retrieval: bi-encoder, cross-encoder, and Recall@k

A retrieval-augmented model answers from two memories. One memory sits in the weights. The other is a corpus you can edit, re-chunk, and re-index without another training run. Lewis and colleagues describe that system as a retriever plus a generator. The retriever selects passages. The generator writes while those passages are in view. This folder is the corpus side of that split. Chunk ids have to stay fixed, because every later number, from a similarity score to Recall@k, names one of them.

The first retriever in this stack is a bi-encoder. A bi-encoder pushes the query through a transformer and pushes each passage through the same transformer on its own. Each call returns a single vector. The passage call does not see the query, so those vectors can be computed once, L2-normalized, and stored. After normalization, cosine similarity is an inner product, and a flat index can scan it by brute force while the collection is small. That independence is the operational point of a bi-encoder: the expensive passage encoding happens offline, and a new question encodes only the query.

Independence is also the limit. Tokens in the query never attend to tokens in the passage, so a near paraphrase can outrank the sentence that actually answers the question. A second model repairs the order. A cross-encoder scores a pair. You pack the query and one passage into one sequence. Self-attention then mixes the two sides, and the network emits one relevance number for that pair rather than a vector you could file in an index. Change the query and every score is invalid. The passage encoding is not reusable across queries, which is why a cross-encoder is the wrong object to precompute.

The cost of that joint forward pass is why the cross-encoder runs on a shortlist. A retrieve step, the bi-encoder or a lexical index or both, nominates a few dozen chunks. The second stage is a re-rank: the cross-encoder scores only those candidates and the caller keeps the new top of the list. In the pipeline this corpus is for, the shortlist is about twenty fused hits and the cross-encoder keeps five. Scoring every chunk would repeat a full pairwise pass per chunk. That is the wrong shape for interactive search even when the collection is only a handful of notes. The shortlist is the stage where the pair model stays affordable.

Recall@k checks the first stage, not the taste of the re-rank. It is 1 when a labeled chunk id shows up anywhere in the top k, and 0 when it does not. A re-rank can move a relevant id upward inside the list it was given. It cannot recover an id the retriever dropped. If Recall@k is 0 on the shortlist, the cross-encoder never sees the right text, and the final list stays wrong. That is why Recall@k is logged on the bi-encoder, on the lexical list, and on the fused list before anyone celebrates a prettier order.

The windows in this corpus are character spans. The default width is 800 characters with an overlap of 120. The end of a window snaps back to a space in the last 80 characters when one exists, so a cut prefers a word boundary. Overlap keeps a sentence that straddles a cut inside two neighboring chunks. The id is the filename stem, a colon, and the window index starting at 0. `retrieval-notes:0` has to mean the same string after a rebuild, or a later labeled set becomes a guess. Overlap must be smaller than the window. An empty note contributes no rows.

Passage vectors from the bi-encoder are what the local dense index stores. Query vectors are the only ones computed at search time. The cross-encoder never writes those vectors. It only re-scores pairs that the earlier stage already returned. Keep that order straight when a latency number shows up: embedding the corpus is a one-time cost, and the pair model is a per-query cost on a short list.
