# Fieldguide runbook

Fieldguide is one local system in four processes. Leave the ports and the JSON fields as they are. The retrieval service listens on port 8000. Liveness is GET /health. The body is a status of ok and the number of chunks currently loaded. Search is POST /search. The request carries a query string and a k. The response carries hits. Each hit has an id, the chunk text, and a rerank_score from the second-stage scorer. Clients send that shape. The service loads its indexes once at startup. Rebuilding the chunk file is an offline step. POST /search does not rewrite the corpus.

The token service listens on port 8001. It exposes a chat-completions route whose body is a server-sent event stream. Each event line carries a choice with a delta content string, and the stream ends with a done sentinel. The voice process listens on port 8010 at the WebSocket path /ws. The message types for that socket live beside the voice code. The browser page is static and is served on port 5500. These processes bind to loopback. This runbook does not assume a public host.

Assistant answers in the supervised set are short on purpose. A labeled assistant turn is 2-4 sentences. That band is long enough to state the fact and the reason, and short enough that a small model can learn the rhythm. The same band is what we want once a generator is wired to POST /search: ground the reply in a returned hit, then stop. A hit should not be padded into a long essay, and a question that asks for a reason should not come back as a single noun phrase. The 2-4 sentences rule is the writing rule for labeled rows and the reading rule for anyone judging a generation. Count sentences, and keep the character length of those rows inside the band the validator will enforce later.

The corpus behind the retrieval service is three markdown notes, cut into character windows, and stored as JSON lines. An id is a filename stem, a colon, and a zero-based index. Hybrid search keeps a dense index and a lexical index on those same ids, then fuses the two rankings. Reciprocal rank fusion uses a constant k of 60. The score added for a list is one divided by k plus the rank, and ranks start at 1. A document missing from one list does not receive a term from that list. Ties break by id. That constant is a rank smoother. It is not a cosine, and it is not the k on POST /search. The request k is how many hits to return. The fusion k only shapes the combined rank score.

Run the retrieval code from its own virtualenv. The fine-tune environment and the speech environment are separate, because those dependency sets do not solve cleanly together. Model weights, adapters, and the vector index stay on disk and out of git. Notes, JSON lines, and metric files stay in the tree. If a download asks for a Hugging Face login, the token stays in the local credential store and never in a committed file. A blank metric stays blank until the command has been run. Copy the number from the terminal. Do not refill it from memory on a later day.

A healthy retrieval check looks like this. GET /health returns ok and a chunk count that matches the JSON lines file. POST /search for a question these notes can answer returns a hit whose id prefix is the note that contains the fact, and the hit text actually contains that fact. Latency and recall belong in the eval folder as JSON before they are copied into the activity log. When a job later rebuilds the index, a failed job must leave the previous chunk file and the previous index in place. A path that escapes the raw notes directory is a failed job, not a search.
